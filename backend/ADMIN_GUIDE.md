# 사용자 관리

관리자 화면은 `/admin/users`, 문서 활동 기록은 `/admin/activity`입니다.
로그인한 사용자의 현재 DB 직급이 `ADMIN`이고 계정 상태가 `ACTIVE`여야 이용할 수 있습니다.
로그인 후 홈 화면(`/`)에서 부서 탭·공지와 문서 목록으로 바로 이동합니다.
문서 작성·검토와 관리자 메뉴는 현재 DB 직급과 부서 배정에 따라 표시됩니다.

## 제공 기능

- 아이디·이메일 검색, 부서·직급·계정 상태 필터, 페이지당 20명 조회
- 직급 임명 및 소속 부서 변경·미배정 처리
- 보안 등급 배정, 전체 공지 관리, 부서 이름 변경·이관·폐쇄
- 본인 확인 후 일회용 비밀번호 복구 링크 발급
- 밴, 잠금, 정상 복구, 계정 삭제
- 기존 `departmentcreate.html`의 `departmentForm`을 재사용한 부서 생성
- 전체 부서의 문서 작성·열람·검토 화면 열람·승인·반려 기록 조회
- 문서 활동의 사용자·문서·활동 종류·검색어 필터, 페이지당 30건 조회

## 설계와 범위

`AdminUserController`는 폼 검증과 화면 이동, `AdminUserService`는 권한·상태 변경을 담당합니다.
입력은 `UserAssignmentRequest`에 받으며 사용자의 비밀번호·아이디·계정 상태를 임명 폼에서 변경할 수 없습니다.
각 서비스에서도 현재 DB 사용자의 권한을 검사합니다. 화면이나 세션의 직급만으로 허용하지 않습니다.

삭제는 `DELETED`로 변경하는 논리 삭제입니다. 작성자·검토자와 연결된 사용자 행, 문서, 활동 기록을 보존하며
로그인을 영구 차단합니다. 삭제된 계정의 복구·재임명은 허용하지 않습니다. 밴과 잠금은 정상 복구할 수 있습니다.
현재 저장된 상태값과 호환되도록 정지 상태의 DB 이름은 기존 `BAN`을 유지했습니다.
Flyway 마이그레이션이 기존 계정·문서 데이터를 보존하면서 스키마를 갱신합니다. Hibernate는 `validate`로 구조를 검사합니다. 운영 DB를 자동으로 다시 만드는 설정은 사용하지 않습니다.

관리자는 자기 직급을 내리거나 자기 계정을 정지·잠금·삭제할 수 없습니다.
관리 변경 시 관리자 행을 ID 순서대로 잠가, 동시에 서로를 정지하는 작업이 마지막 정상 관리자를 없애지 못하게 합니다.
`CurrentAccountFilter`는 매 요청에 DB 상태와 직급을 반영하여 밴·삭제·강등을 기존 세션에도 적용합니다.
변경 직전에 이미 실행 중이던 요청을 강제로 중단하지는 않습니다.

문서 활동은 `DocumentActivity`에 활동 시점의 사용자·직급·문서 제목·버전·시간을 저장합니다.
비밀번호나 문서 본문을 기록하지 않습니다. 문서 작업과 기록 저장은 같은 트랜잭션에서 성공하거나 롤백됩니다.
계정 삭제 또는 직급 변경 후에도 이전 기록의 정보가 유지됩니다.
기록 기능 도입 전의 열람 기록은 복원할 수 없고, 현재 기록은 성공한 문서 작업을 대상으로 합니다.
로그인 성공·실패, 권한 거부, 사용자 관리와 업무 변경은 별도 `audit_record`에 저장합니다. `/admin/audit`에서 전체 감사 기록과 HMAC 체인 무결성을 검사할 수 있습니다. 문서 활동 기록 화면도 유지합니다.

신규 패키지는 `admin`, `activity`, `security`처럼 소문자입니다.
기존 `User`, `Department`, `Document` 패키지는 이번 작업에서 일괄 변경하지 않았습니다.

## 실행과 첫 관리자

[LOCAL_GUIDE.md](LOCAL_GUIDE.md)의 실행·최초 관리자 절차를 사용하세요. 본인 PC에서 만든 `admin` 계정도 기존 비밀번호를 확인한 뒤 권한을 올릴 수 있습니다. 클라우드에서 사용자의 PC DB를 직접 변경하지는 않습니다.

최초 관리자 설정은 서버를 종료하고 `backend`에서 `scripts/bootstrap-admin.ps1`(Windows) 또는 `bash scripts/bootstrap-admin.sh`(Linux/macOS)를 실행합니다. 이미 관리자가 있으면 사용자 관리 화면에서 임명합니다. 회원가입은 항상 일반 계정을 만들며 기본 관리자 비밀번호는 없습니다.

## 관리자 문서 즉시 승인

관리자가 작성·제출한 모든 문서는 등록 즉시 승인됩니다. 프로젝트 문서와 기밀·제한 문서도 동일하며 `AUTO_APPROVED` 의견, 승인 활동, 감사 기록을 남깁니다. 관리자 초안 저장은 승인으로 처리하지 않습니다. 일반 작성자는 기술 검토와 필요한 보안 승인을 받습니다.

이 정책은 프로젝트 최종 배포의 품질시험·보안 검토·필수 문서·미해결 변경 및 부적합 검사를 생략하지 않습니다. 품질·보안 판정에는 독립된 계정이 필요합니다.

## 부서 탭과 공지

홈 화면의 **부서 탭·공지** 바로가기로 `/departments`에 진입하며, 부서 화면의 **홈** 메뉴로 돌아옵니다.
`/departments`에서 부서 탭과 공지 게시판을 이용합니다. 부서 목록을 DB에서 조회하므로 기존 부서와 새로 생성한 부서는 별도 등록 없이 탭으로 표시됩니다.
관리자는 전체 부서, 일반 사용자는 현재 배정된 부서만 볼 수 있습니다. 부서가 없는 사용자에게는 배정 안내를 표시합니다.
부서 생성 후 관리 화면에서 생성한 부서 탭으로 바로 이동할 수 있습니다.
단독 생성 화면(`/dep/create`)에서는 등록 성공 후 생성한 부서 게시판으로 이동합니다. 게시판에서 새로고침해도 생성 요청이 다시 전송되지 않습니다.

공지는 관리자 또는 해당 부서의 과장 이상이 작성·수정·삭제하고 부서원은 열람합니다. 일반 사용자는 다른 부서의 주소를 직접 입력해도 접근할 수 없습니다.
제목은 255자, 본문은 10,000자까지 일반 텍스트로 저장하며, 목록은 최신순으로 페이지당 20건입니다.
작성자는 로그인한 계정에서 결정됩니다. 변경 요청은 CSRF 검증과 현재 DB 권한 확인을 거치며, 오래된 수정·삭제 화면은 충돌로 처리해 새 변경을 덮어쓰지 않습니다.
공지 데이터는 `department_notice` 테이블에 저장됩니다. Flyway가 서버 시작 시 필요한 스키마를 갱신하며 부서·계정·문서 데이터는 유지됩니다.

## 검증

문서 목록은 `/document/list`에서 확인합니다. 작성·상세·검토·관리 화면에서 목록으로 이동할 수 있습니다.
문서별 최신 버전을 최신 등록순으로 기본 페이지당 20건 표시하며, 부서·열람 등급·승인 상태에 따른 상세 열람 권한을 동일하게 적용합니다.
일반 직원은 같은 부서의 승인 문서와 본인 문서를, 과장 이상은 등급을 충족하는 같은 부서 문서를 볼 수 있습니다.
관리자는 소속 부서 없이도 전체 부서를 조회합니다. 부서 미배정 직원에게는 배정 안내가 표시됩니다.
목록 조회는 본문과 계정 비밀번호를 가져오지 않으며, 문서 열람 활동으로 기록하지 않습니다.
검토함은 `ReviewQueueItem`, 사용자 목록은 `UserListItem`으로 필요한 표시 항목만 조회합니다.
문서·검토함·사용자·활동 기록·부서 공지 목록은 음수 페이지를 첫 페이지로, 범위를 넘긴 페이지를 마지막 페이지로 보정합니다.
문서 입력은 기존 빈값 검증을 사용합니다. 제목은 기존 화면·요청 제한 50자와 엔티티·DB 제한 255자를 유지하며, 본문에 별도의 글자 수 제한을 추가하지 않습니다.
현재 통합 기능의 변경 파일은 [FEATURE_CHANGES.md](FEATURE_CHANGES.md), 앞선 목록 조회 개선 이력은 [REFACTORING_NOTES.md](REFACTORING_NOTES.md)에 정리했습니다.

```powershell
.\gradlew.bat clean build
```

권한 위조, CSRF, 임명·상태 변경·삭제, 기존 세션 차단, 동시 관리자 변경, 문서 기록 보존과 롤백을 확인합니다.
