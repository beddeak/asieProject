# 문서 변경 후 배포 차단 · 2026-10-10

## 해결하는 문제

공유 폴더·메일·수기 승인으로 기술 문서를 관리하면 설계가 개정된 뒤에도 이전 문서를 대상으로 한 시험 결과를 새 배포에 사용하는 실수가 생길 수 있습니다. AegisVault는 품질시험·보안 검토를 **검증 당시 문서 구성**에 연결하고, 현재 배포 구성과 일치하는지 서버에서 확인합니다.

기존 기업용 문서 관리 제품 전체에 없는 기능이라는 주장은 하지 않습니다. 이 작품의 시연에서는 **문서 변경 → 이전 검증으로 배포 차단 → 현재 구성 재검증 → 배포 성공**이라는 업무 흐름을 보여줍니다.

## 화면에서 확인하는 내용

프로젝트 → 연구개발·품질·보안 → 최종 배포에서 다음을 확인합니다. 품질시험·보안 검토 탭에도 같은 비교 화면이 있습니다.

- 품질시험과 보안 검토의 현재 유효 상태를 각각 표시합니다.
- 변경된 문서는 `검증 당시 v1 → 현재 v2`처럼 표시하며 양쪽 버전을 열 수 있습니다.
- 검증 이후 추가된 문서와 현재 배포 대상에서 제외된 문서도 구분합니다.
- 열람 권한이 없는 초안은 제목과 링크를 숨기고 `현재 v2 · 열람 제한`으로 표시합니다. 해당 초안을 읽을 수 있는 작성 담당자는 제목과 링크를 볼 수 있습니다. 문서가 승인되면 품질·보안 담당자도 현재 버전을 열 수 있습니다.
- 품질시험·보안 검토 화면으로 이동해 현재 구성을 검증할 수 있습니다.
- 이전 시험 결과는 이력으로 보존하고, 현재 배포 근거로 사용할 수 없다는 안내를 표시합니다.

## 시연 순서

로컬 실행·계정 설정은 [LOCAL_GUIDE.md](LOCAL_GUIDE.md)를 따릅니다. 관리자 문서 작성자, 품질 담당자, 보안 담당자는 서로 다른 계정을 사용합니다.

1. 프로젝트에 설계서·시험 보고서·보안 검토서를 작성·승인합니다. 관리자가 제출하면 기존 정책에 따라 즉시 승인됩니다.
2. 시험 기준을 등록하고 품질 적합 결과 및 독립 보안 승인을 기록합니다.
3. 책임자가 프로젝트를 배포 검토 상태로 전환합니다. 최종 배포 화면에서 두 검증이 현재 구성에 유효하고 배포 조건이 충족됐는지 확인합니다.
4. 설계서 상세에서 새 버전을 만들고 내용을 변경해 제출합니다. 기존 문서와 검증 기록은 남습니다.
5. 최종 배포로 돌아가 `v1 → v2` 변경과 두 검증의 재검증 필요 상태를 확인합니다. 새 버전이 승인됐어도 이전 시험·보안 결과만으로는 배포할 수 없습니다.
6. 품질 담당자가 현재 문서를 확인하고 새 시험 결과를 등록합니다. 보안 검토가 남아 있어 배포는 계속 차단됩니다.
7. 보안 담당자가 현재 구성에 대한 검토를 승인합니다. 책임자가 프로젝트를 다시 배포 검토 상태로 전환합니다.
8. 나머지 필수 조건도 충족했다면 수신자를 지정해 배포합니다. 배포에는 새 문서 버전과 새 검증 기록이 연결됩니다.

이 흐름에서 승인된 문서에 새 초안을 만들기만 해도 최신 버전은 미승인 상태이므로 배포가 차단됩니다. 이미 확정한 과거 배포의 문서 버전은 바뀌지 않습니다. 과거 배포를 중단해야 한다면 별도의 배포 회수 기능을 사용합니다.

| `workflow/ReviewEvidence.java` | 당시 버전과 현재 버전을 비교하고, 유효·재검증·미검증·실패 상태를 판정합니다. |
| `release/ReleaseGate.java` | 같은 판정으로 화면과 서버의 배포 차단 사유를 구성합니다. 기존 필수 문서·부적합·독립성·파일 검사도 유지합니다. |

| `Document/DocumentService.java`, `DocumentVersionRepository.java` | 문서 목록·이력과 같은 SQL 열람 조건을 사용해 비교 대상 버전의 제목과 링크 권한을 한 번에 확인합니다. 문서마다 별도 조회하지 않습니다. |
| `workflow/WorkflowController.java` | 품질·보안·배포 탭에 공통 비교 결과를 전달합니다. 검토 폼과 비교 화면에 동일한 현재 구성을 사용합니다. |

Java 경로는 `src/main/java/com/asie/aegisvault/`, 화면·DB 경로는 `src/main/resources/` 기준입니다.

## 과거 데이터 처리

업데이트 이전 시험·보안 기록에는 당시 문서 목록이 없고 구성 식별값만 있습니다. 과거 버전을 추정해서 채우지 않습니다. 기존 식별값으로 배포 가능 여부는 계속 확인하며, 이전 구성과 다르지만 상세 기준 기록이 없으면 그 사실을 화면에 설명합니다. 업데이트 후 수행한 검증부터 정확한 문서별 변경 비교가 제공됩니다.

문서 버전이 같아도 필수 문서 수량·시험 기준 등 검증 조건이 바뀌면 재검증이 필요합니다. 이 경우 문서 버전이 바뀐 것처럼 표시하지 않습니다.

## 검증

Java 21에서 전체 `build`와 **276개 테스트**가 통과했습니다. 실패·오류·건너뜀은 0건입니다.

- 통합 테스트: 변경 없는 조회는 유효 상태 유지, 초안 생성 시 차단, 관리자 제출 즉시 승인 유지, 이전 요청 409·이전 검증 재사용 요청 400, 품질만 갱신 시 계속 차단, 양쪽 재검증 후 새 버전 배포, 이전 검증 이력 보존을 확인합니다. 초안 제목·링크의 사용자별 열람 차이와 보안 등급 회수 후 403도 확인합니다.
- 비교 단위 테스트: 문서 개정·추가·제외, 문서 버전이 같은 검증 조건 변경, 기준 목록 없는 과거 기록, 품질·보안의 독립 판정을 확인합니다.
- DB 이전 테스트: V2의 시험·보안·배포 기록을 보존하고 V3에 임의 기준 기록을 채우지 않는지, 참조·중복·소유자 제약이 적용되는지 확인합니다.

실제 Chromium에서도 별도의 부서·프로젝트·계정을 만들어 위 시연을 수행했습니다. 초안 제목·링크의 열람 제한, 문서 변경 후 배포 차단, 두 담당자의 재검증 후 새 버전 배포까지 확인했습니다. 데스크톱과 390px 모바일에서 버전 비교·재검증 이동을 확인했으며 가로 넘침·JavaScript 오류·HTTP 500은 없었습니다.
